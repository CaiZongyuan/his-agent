【**摘要**】随着 AI 智能体（agent）在复杂、长程推理方面的能力日益增强，严格的评估对于衡量其向真实医疗应用迈进的进展至关重要。然而，现有的医疗基准往往趋于饱和、静态化或临床覆盖面狭窄，限制了它们区分前沿系统或追踪进展的能力。我们提出 HealthAgentBench，一套包含 54 个智能体式医疗任务、横跨 7 个类别的基准套件，每个类别拥有其独特的环境。该基准套件覆盖了患者诊疗全程中多样化的工作流，以及广泛的数据模态。每个任务都旨在复现端到端的临床工作流：在仅给出最简指令的情况下，智能体必须探索原始医疗数据、在复杂环境中操作，并执行超越朴素提示的多步解决方案，例如查询大型临床数据库或解读十亿像素级病理图像。所有任务均根据专家推导的标签或人类表现，采用二元成功/失败标准进行评分。最终报告的任务成功率提供了一个单一、可解释的度量，用于衡量每个智能体在 HealthAgentBench 上的整体表现。在前沿智能体上评估 HealthAgentBench，我们发现整体任务成功率仍然偏低，突显了该套件的难度。表现最强且最具性价比的智能体 Codex GPT-5.5 仅达到约 42% 的成功率。除整体表现外，HealthAgentBench 还揭示了各任务类别中细腻的优势与不足。前沿智能体在基于 EHR 数据自动构建研究建模流水线方面展现出潜力，但医学影像仍尤其具有挑战性，尤其是 Claude Code 系列模型，而 Codex GPT-5.5 则展现出新兴能力。将大型搜索空间与组合推理需求相结合的任务对当前所有智能体而言仍然困难。综上，这些结果表明 HealthAgentBench 提供了一个具有挑战性且贴近现实的基准，并为未来的进展留有巨大空间。我们在 [https://github.com/microsoft/HealthAgentBench](https://github.com/microsoft/HealthAgentBench) 发布了我们的基准。

# 引言
---

AI 研究领域正在经历一场转型：从将大语言模型（LLM）作为孤立的任务求解器，转向能够在复杂环境中执行动作的智能体式（agentic）系统。传统的 LLM 基准主要围绕静态输入设计：模型接收一个固定的提示（通常包含一段简短的文本上下文），并给出单一答案。例如，**MedQA 等任务评估的是 LLM 能否在给定一段简明临床病例的情况下回答一个问题。**如今，配备了工具、执行框架（harness）和运行环境的 LLM 智能体已能超越固定上下文的提示方式：它们可以搜索、检查、查询、计算，并针对分布于文件、数据库、图像和软件系统中的数据进行迭代式操作。因此，开发智能体式评估环境已成为准确衡量这些前沿系统能力的关键。



这一转变对医疗领域尤为重要，因为许多高价值应用都需要在复杂、多模态、大规模数据上完成端到端推理。支撑真实临床工作流往往需要处理无法用简短提示完整表达的信息，例如 3D CT 体数据、十亿像素级病理切片、纵向 EHR 数据库、试验方案，以及异构的临床文档。这些场景在历史上一直超出传统提示方法的能力范围，要么因为数据超出了模型的上下文窗口，要么因为解决任务需要与工具和环境进行多步交互。智能体式系统通过让模型探索环境、操作原始数据，并设计执行针对特定任务的策略，为更真实地应对这些工作流创造了可能。



因此，超越静态评估、开发贴近现实且整体的基准套件，以评估智能体在端到端医疗任务上的新兴能力，至关重要。然而，当前的医疗基准格局仍然碎片化，不足以评估 AI 智能体的全部能力。传统基准主要衡量孤立的推理或问答能力，而近期面向智能体的工作往往范围受限，常常聚焦于特定任务、模态或预定义工作流。这种缺乏广泛、原生智能体式（agent-native）评估的局面，使得我们难以就前沿系统在医疗领域的能力得出可靠结论，因为**真实世界的临床工作流几乎从不依赖单一任务、模态或数据源（例如，临床医生通常会整合来自多种输入的信息——如病理切片、CT 扫描、放射科报告等——以得出诊断和治疗的决策）。**因此，亟需一个全面、贴近现实且具挑战性的基准套件，为评估和比较医疗领域的智能体式 AI 系统提供共同基础，使研究人员能够识别优势与待改进之处，并追踪这一快速演进领域的进展。



在本研究中，我们提出 HealthAgentBench，一个用于评估 AI 智能体的统一智能体式医疗环境套件。**HealthAgentBench 由 54 个任务组成，横跨 7 个类别，每个类别拥有其独特的环境，包括 X 光胸片报告修正（X-ray Report Correction）、病理全切片图像肿瘤区域选取（Pathology Tumor Area Selection）、胸部 CT 异常分类（CT Abnormality Classification）、临床试验匹配（Clinical Trial Matching）、EHR 数据质量审计（EHR Data Quality Auditing）、EHR 事件建模（EHR Event Modelling）和 EHR 格式转换（EHR Format Conversion / ETL 管道定制）。**这些任务覆盖了患者诊疗全程中多样化的临床工作流，包括数据管理、诊断、研究和治疗规划。它们还**涵盖了广泛的数据模态，包括 2D 放射影像、3D CT 体数据、全切片病理图像、自由文本和结构化临床数据。**如相关章节所述，我们提供了一套原则性的工作流来选择和创建 HealthAgentBench 中的每个任务，以确保这一统一基准是真实、具挑战性、可验证且多样的。



对于每个任务，我们**遵循 TerminalBench 的设计，提供基于终端（terminal-based）的环境**（见图1）。在每个环境中，**智能体会获得真实的临床产物，包括患者数据和支持性资源，以及最简的任务指令。**这种设置让智能体能够自由探索环境、制定策略并提出解决方案。X 光胸片报告修正（X-ray Report Correction）任务（见图1）向智能体提供一个环境，其中包含某位患者纵向的胸部 X 光病史和一份损坏的报告，智能体可以查看、放大、裁剪放射影像，并在撰写修正报告前交叉参考既往研究。通过这种方式，HealthAgentBench 评估智能体的端到端自主能力，包括规划、工具使用、环境探索和任务执行。再举一个例子，当面对一个 CT 体数据时，智能体可以选择依次检查切片、安装图像处理工具、预先筛选相关区域，或在给出最终预测前裁剪候选病灶。最后，我们提供了一个统一的评估模块，针对人类表现或专家标签为每个任务定义成功/失败标准，从而评估智能体输出，实现对整个套件中各智能体的一致比较。我们进行了人工复核，以确保这些成功标准是可达成的。



![](https://cdn.nlark.com/yuque/0/2026/png/1739170/1786605998346-e1428dca-88e1-4767-9744-2379704706ef.png)

> **图1：HealthAgentBench——面向智能体医疗AI的统一评估框架。**每个基准测试任务都被封装为一个Docker容器环境，包含三个阶段：
>
> (1) 容器通过将患者数据及必要工件暂存于 `/data/` 下以设置环境（此处，**X光报告**修正任务包含一名患者的纵向胸部X光历史记录，其中目标检查的报告带有损坏的初稿“发现”部分，智能体必须予以修正）；
>
> (2) 智能体接收一条自然语言指令；
>
> (3) 智能体在终端中操作，发起工具调用（它可自由决定是否安装软件包或运行命令，以查看、裁剪和放大图像，或查阅该患者的既往检查资料），直到将修正后的报告写入 `/workspace/submission.json`。评估在容器外部进行，依据隐藏的专家审核真实答案及二元成功标准进行评判。同一容器化框架实例化了全部7个任务类别（右图），每个类别均处于独特的环境之中，图中还显示了每个类别的输入模态和任务数量。

我们使用 HealthAgentBench 对前沿 LLM 智能体开展了一项实证研究。我们发现，即便对最先进的系统而言，这些任务也极具挑战性，表现最强的智能体 Codex GPT-5.5 仅达到约 42% 的任务成功率。除这一整体结果外，该套件还支持对各任务类别、临床工作流和数据模态上智能体优势与不足的细腻分析，凸显了当前智能体展现潜力的领域，以及仍需大幅进展的领域。



综上，我们的贡献如下：

1. **统一的智能体式医疗环境套件。** 我们提出 HealthAgentBench，一个用于在真实、以患者为基的任务上评估 AI 智能体的基准套件，这些任务横跨多样化的临床工作流和数据模态，包括医学影像、自由文本和结构化 EHR 数据。我们还建立了一套原则性的工作流，用于为该基准发掘和筛选任务，该工作流可扩展至未来的版本。
2. **远离饱和、极具挑战性的基准。** HealthAgentBench 旨在衡量前沿医疗智能体随时间推移取得的进展。当前前沿智能体的整体任务成功率偏低，表现最强的模型 Codex GPT-5.5 仅达到约 42%，为未来的改进留有巨大空间。
3. **对前沿智能体能力的细腻分析。** 我们的基准揭示了当前前沿智能体的两大瓶颈：（i）医学影像任务（即 CT、X 光、病理切片）；（ii）需要大型搜索空间与复杂组合推理的任务。我们进一步观察到清晰的模型家族差异：Codex GPT 系列模型（尤其是 GPT-5.5）通常更具性价比，并在医学影像任务上持续优于 Claude Code 系列模型。

# 相关工作
---

医疗领域面向智能体的基准正在快速增长，但尚无任何一个提供一套统一的、可执行的、跨越患者诊疗全程的多模态评估。我们将近期工作归为三条互补的研究脉络，并讨论 HealthAgentBench 与每条脉络的关系。



第一条研究脉络**关注智能体策略如何改进医学问答**。两个代表性例子是 **MedAgentBoard**，它对 LLM 多智能体协作与单 LLM 提示以及跨医学任务族类的强力传统方法进行了细致比较；以及 **ClinicalAgent Bench**，它考虑了一个横跨五个临床能力维度、并配备丰富临床工具箱的广泛任务套件。这些基准主要围绕问答形式组织，其中每个实例将一个查询与预先提供的上下文配对，而智能体的工具或协作者作为求解器的一部分运作 HealthAgentBench 的侧重点不同：**智能体并非回答一个自包含的问题，而是必须在一个实时环境中探索并采取行动，并随多步操作改变该环境的状态。**



第二条研究脉络开发了**以临床对话为中心的真正交互式评估。HealthBench 和 HealthBench Professional 为多变的患者与临床医生对话提供了精心构建、由医生撰写的评分准则**；MAI-DxO 将诊断建模为一个在艰难的 NEJM 病例上、具有成本意识的顺序过程；AgentClinic 则将医学 QA 和 EHR 病例转化为一个带有互动的医生、患者和测量智能体的模拟诊室。本着类似的精神，AI Hospital、MedAgentSim 和 CP-Env 等模拟医院环境让模型在多步就诊和分支诊疗路径中扮演临床人员。这批工作尤其出色地刻画了临床推理与沟通。其重点是会话式与模拟患者的交互，而 **HealthAgentBench 要求智能体直接对原始、异构的患者数据操作。**



第三条研究脉络与我们最为接近，**它将智能体置于真实数据上的可执行环境中，每个基准聚焦于特定的临床场景。**

+ **MedAgentBench 与较新的 PhysicianBench 将智能体置于基于 FHIR 的 EHR 中，以检索记录和下达医嘱，**
    - **其中 PhysicianBench 将该范式扩展到长程、执行可验证的工作流；两者都以结构化 EHR 数据为核心。**
    - **MedAgentGym 提供了一个可扩展的智能体式环境，用于围绕生物医学数据科学任务、以代码为中心的推理，强调对结构化记录的程序化分析。**
+ **AutoMedBench 和 CamylaBench 与我们对端到端原始数据流水线的重视一致**，但它们**规定了分阶段的工作流，而非让智能体自主探索，并且主要聚焦于医学影像。**
+ HealthAdminBench 则研究计算机使用（computer-use）智能体在医疗行政工作流上的表现。HealthAgentBench 通过将这些工作的优势统一为一个单一、广泛、可执行的基准来对其形成补充，在该基准中智能体自主地与真实、异构的患者数据交互。该套件覆盖五种数据模态（2D 放射影像、3D CT 体数据、病理全切片图像、自由文本临床文档和结构化 EHR 记录）以及临床工作流的四个主要阶段：诊断、数据管理、研究和治疗规划。
+ 通过采用带最简指令的基于终端的环境，HealthAgentBench 借鉴了 Terminal-Bench、OSWorld、GAIA 和 WebArena 等通用领域智能体基准的设计理念，同时将其适配于医疗特有的多模态数据、复杂工作流和专门工具。（见图2）将 HealthAgentBench 相对于现有医疗智能体基准的定位沿两个维度呈现：交互真实度与覆盖广度。HealthAgentBench 独特地结合了真实的智能体交互与对临床模态和工作流阶段的广泛覆盖，填补了当前评估格局中的一项关键空白。

---

1. 包括 X 光胸片报告修正（X-ray Report Correction）、
2. 病理全切片图像肿瘤区域选取（Pathology Tumor Area Selection）、

## 任务筛选标准


要被纳入 HealthAgentBench，一个候选任务必须满足以下标准。

+ **Agentic Workflow（智能体工作流）** 我们刻意选择那些需要智能体（agentic）工作流的任务，这类任务可能包含规划、工具使用、多步推理或环境交互，单纯的单次 LLM 提示无法完成。例如，LLM 无法将整卷 CT 体积或整张病理切片整体塞入提示词中。
+ **Realistic Clinical Workflow（真实临床工作流）** 这些任务覆盖临床工作流的不同阶段，包括**数据管理（EHR 格式转换、EHR 数据质量审计）、诊断（X 光胸片报告修正、病理全切片图像肿瘤区域选取、胸部 CT 异常分类、临床试验匹配）、事件建模（EHR 事件建模）以及治疗规划（临床试验匹配）。**所有任务都包含真实的临床数据，包括患者数据或临床文档（如试验信息）。
+ **Wide coverage of modalities and environments（对模态与环境的高覆盖度）** 我们的任务套件旨在跨越多样化的医疗场景与环境。下图（见相关图7）概括了 HealthAgentBench 在多个维度上的覆盖情况，包括输入模态、临床工作流、输出格式、患者与时间范围，以及数据访问机制。HealthAgentBench 跨越五种输入模态——二维 X 光片、三维胸部 CT、病理全切片图像、自由文本临床文档以及结构化 EHR 数据。其任务还覆盖了多样的智能体输出格式，包括叙述性报告、排序列表、分类结果，以及工程化解决方案，如 ETL（抽取、转换与加载）管道或标记出的数据质量问题。该套件还在患者范围上有所不同，从单条记录的推理到队列规模的分析，并包含需要跨越按时间排序的事件进行推理的纵向任务。
+ **Verifiable with low chance success rate（可验证且随机成功率低）** 我们优先选择具有客观可验证成功标准的任务，同时确保随机成功率较低。特别地，我们排除了具有均衡标签的单一二分类任务——在此类任务中随机猜测即可达到 50% 的成功率。多标签二分类任务被保留，因为智能体必须做出多个相互独立的预测，从而正确猜中全部标签的概率呈指数级下降（例如，在胸部 CT 异常分类中，智能体必须正确识别 CT 体积中每一种异常存在与否才能通过任务）。因此，HealthAgentBench 中任务的随机猜测成功率很低——通常低于 10%——确保性能真正反映智能体的能力，而非运气。

## 任务来源


候选任务来自两个来源。首先，我们利用带有专家标注或报告的现有基准，将其转化为基于终端的智能体环境。我们重新设计了智能体可见的接口，使得智能体必须通过自主探索端到端地解决任务，而不依赖原始基准评测中所用的人工脚手架或任务专用工程。例如，EHR 事件建模改编自 EHRSHOT。EHRSHOT 最初是为人类研究者开发预测模型而设计的，而我们的版本要求智能体执行完整的机器学习工作流——从探索患者数据库、选择建模策略，到训练模型并在测试集上生成预测——从而将其转变为一项难度显著更高的智能体评测。我们也通过对患者数据进行基于规则的增强或管道封装来创建新任务。其次，我们通过增强精心整理的患者数据集，或将已有的临床管道封装为可执行环境来创建新任务。例如，EHR 数据质量审计是通过使用基于规则的扰动向 MIMIC-IV 数据集中注入真实的数据质量问题而构建的，例如不可能的生理数值、相互矛盾的临床记录以及人口统计学冲突。智能体必须检查底层的患者数据、识别被注入的错误，并报告相应的数据质量问题。

## 任务设计原则


每个任务都围绕以下设计原则构建：

1. **Versatile terminal environment（通用终端环境）。**我们利用 harbor 框架将每个任务打包为一个终端环境，以适配该套件所跨越的异构原始患者数据格式。终端环境提供了一个灵活的接口，智能体可以通过它检查异构数据格式、调用领域专用软件、查询数据库，并在大规模资源上编排复杂的工作流。它们也与当今前沿编码智能体的执行环境高度契合——这些智能体主要被设计并优化为通过终端接口运行。这使得终端环境成为在真实临床任务上评估自主智能体能力的天然载体。（注：我们选择终端接口的动机在于评测而非部署。在实际临床系统中，智能体可以在后端通过终端或执行环境运行，同时通过面向临床医生的图形界面呈现其输出。）
2. **Efficient, representative sampling（高效、有代表性的采样）。**我们不会发布数百个相似的任务，而是采样一小批（通常每个任务类别 5–15 个样本）具有代表性的样本（例如覆盖不同疾病类型、不同难度级别），使得对本基准中所有任务的一次完整遍历能够在合理时间内产生有意义的信息。
3. **On-the-fly data download（按需数据下载）。**我们不会重新分发数据与标签，而是提供一键运行脚本，在用户提供凭据后于运行时从原始来源获取数据。
4. **Anti-cheat by construction（从构建层面防作弊）。**黄金标签与验证器代码只挂载到验证步骤中，绝不进入智能体容器。智能体可见的标识符被设为不透明（例如 $ \texttt{case_NN}、\texttt{study_NN_<timestamp>} $ ），语料库名称从文件名中抹去，使得智能体无法回溯到上游数据集并查找到答案。我们还禁用了智能体的网页浏览能力，以阻止其通过浏览互联网获取黄金标签。
5. **Minimalist instructions（极简指令）。**面向智能体的提示词只用寥寥数句说明目标，但将策略（读取哪些文件、以何种顺序、调用哪些工具）完全交由智能体自行决定，而非预先定义工作流。这样，我们能够在测试智能体执行能力的同时，检验其内在的规划与策略制定能力。
6. **Determine task-specific success criteria（确定任务专用的成功标准）**每个任务都使用二元的成功/失败标准进行评估，同时报告任务专用的性能指标。成功标准针对每个任务类别分别确定；附录中的相关表格概括了这些标准，而附录中各任务的 _Scoring_（评分）段落给出了完整细节。这些标准可分为几大类：_完全或整体正确性_（每个 CT 异常标签都正确，或所有 ETL 验证器检查都通过）、对目标的_穷尽恢复_（在数据质量和试验匹配任务上的完整召回）、_无错误的输出_（报告修正中零临床显著性错误），以及_达到性能阈值_——既可以是绝对指标截断值（肿瘤 tile-F1 ≥ 0.90），也可以是匹配人类工程化基线（AUROC 达到或超过人类工程化的 count+GBM 模型）。在任何情况下，阈值都被设定为：成功即代表一个近乎专家水平、真正有用的解决方案。这一设计使得整个套件中的多样化任务得以在一个统一的评估框架下评测。我们使用整体任务成功率（即智能体成功解决的基准任务所占比例）作为衡量智能体整体进展以及进行任务间比较的主要指标。任务专用指标（如 F1 和召回率）会与任务成功率一并报告，以量化部分进展并额外洞察智能体的性能。

## 创建后检查


在任务被加入套件之前，我们会对多个前沿智能体运行一次基线遍历，并检查其轨迹。我们_借助人工与 LLM 辅助_审查智能体的交互记录，以捕捉两类失败模式：

1. 智能体找到了非预期的捷径（例如将泄露的评测脚本带入智能体容器），这类情况会将任务退回重新设计；以及
2. 任务本身存在真实的歧义，即可能存在多个_合理_的智能体解决方案或替代的有效黄金标签，这类情况同样会将任务退回。

最后还应用一道过滤器：我们_丢弃所有智能体都能轻而易举解决的任务_，只保留那些智能体间成功率差异具有信息量的任务。

## 总体性能


我们评测了来自两个模型家族（GPT-5 系列与 Anthropic 的 Claude 系列）的 10 个前沿智能体，覆盖三种执行框架（Codex、Claude Code 和 Copilot-CLI），均使用超高（xhigh）推理强度并禁用网页浏览能力。图 4 概括了最核心的结果：在 54 个任务上各尝试 3 次（即 162 次试验），**表现最好的智能体（Codex GPT-5.5）仅取得 42% 的任务成功率（意味着只有 42% 的任务被稳定解决），这留下了充足的改进空间，也表明 HealthAgentBench 对当前模型而言是一个具有挑战性的测试平台。**紧随 Codex GPT-5.5 之后的是运行 Opus-4.8 的 Copilot CLI 与 GPT-5.5（分别为 36% 和 35%），然后是最佳的原生 Claude Code 智能体 Opus-4.8（32%）。更小或更老的模型家族则落后更多，最弱的智能体（Codex GPT-5.4-mini）仅取得 16% 的任务成功率。总体而言，该基准揭示出跨连续模型代际的清晰、稳步提升，但距离饱和仍相去甚远。

我们还表明，**智能体执行框架会显著影响性能**。例如，GPT-5.5 的任务成功率从 Codex 下的 42% 下降到 Copilot CLI 下的 35%，而 Opus-4.8 则从 Claude Code 下的 32% 提升到 Copilot CLI 下的 36%。一个可能的原因是 Copilot CLI 采用了多智能体架构，主模型将子任务委派给运行在固定模型后端上的辅助智能体。例如，一个「Copilot GPT-5.5」系统并非一个纯 GPT-5.5 智能体，而是可以调用来自 Opus、Sonnet 及其他硬编码模型的子智能体。

## 优势：EHR 建模的机器学习自动研究


前沿智能体在 EHR 事件建模与 EHR 格式转换上表现突出，这两项任务复现了在表格化临床数据上构建机器学习管道的研究工作流。在 EHR 格式转换（ETL 构建基准）中，智能体的任务是构建一个数据管道，从原始 EHR 数据中提取并转换用药记录。在该基准上，10 个智能体中有 9 个以相对低的成本和较短的执行时间达到了完美的 100% 任务成功率。只有 Opus-4.6 未能通过，因为它持续地从输出转换数据中遗漏了一个人口统计学字段。EHR 事件建模评估了从 EHR 数据构建机器学习管道以进行事件预测的完整流程，因此是一项更难的任务。其成功标准是在一小时的时间预算内达到人类工程化特征工程基线的性能。Claude Code Opus-4.7 以 78% 领先，Codex GPT-5.5 紧随其后为 72%，而大多数智能体都能达到超过 50% 的成功率，这表明端到端的管道构建循环大体已处于当前模型的能力范围之内，前沿智能体在构建 ML 管道的自动研究方面已经能够与人类表现展开竞争性匹敌。值得注意的是，该任务类别中完成一次试验的时间是最长的，这是因为智能体通常在反复尝试不同的模型配置与特征集以寻找最优解。同样引人注目的是，智能体仅借助轻量级机器学习模型（基于原始 EHR 数据进行特征工程）就达到了这一水平——这是考虑到其被限定只有 1 小时时间预算而有意为之的选择——但其逐任务 AUROC 在六个预测目标中的大多数上都匹配或超过了 EHRSHOT 已发表的、基于 CLMBR 神经网络基础模型的基线（见附录D中的相关图12）。



![](https://cdn.nlark.com/yuque/0/2026/png/1739170/1786607737259-830be344-a02d-444d-b953-9c051e033e19.png)

> **图12：EHR事件建模任务中每项任务的测试AUROC：智能体对比CLMBR及count+GBM基线。** 每个条形表示各智能体在六项新发预测目标上的平均测试AUROC。黑色实线标记为EHRSHOT已发表的CLMBR模型在该测试集上的性能；品红色虚线标记为count+GBM基线（基于手工工程化计数特征的梯度提升模型），该基线即为本任务的通过线。两类基线均在与智能体相同的首次预测时间测试队列上进行评分。尽管仅使用了基础特征工程，最佳智能体在每项任务上的表现均达到或超越了基于深度学习的CLMBR基线（两类基线的数值均与EHRSHOT论文[33]中报告的不同，因为我们严格使用每位患者的首次观察数据在子集测试队列上进行评估，以防止数据泄露）。

## 挑战：大海捞针——从复杂搜索空间中完整检索


许多医疗应用需要浏览海量数据以寻找相关信息。临床试验匹配与 EHR 数据质量审计这两个任务类别正是为在不同情境下测试这一能力而设计的。**EHR 数据质量审计要求智能体识别并纠正一个被注入错误后的 EHR 数据集中的错误，这涉及对可能出错之处形成假设，并系统性地排查这些错误。该任务的挑战在于其复杂的搜索空间，涉及 8 张表、共计超过 80 万行。**要正确识别所有错误并非易事，智能体在此举步维艰。没有任何智能体达到超过 50% 的任务成功率（最佳者为 Claude Code Opus-4.6，达到 42%），而除 GPT-5.5 之外的 Codex GPT 模型得分都在 12.5% 或更低。**该任务类别包含八个任务，旨在拆解两个关键挑战：搜索空间与组合复杂性。**为了研究搜索空间，我们比较了四组任务：智能体未获得任何关于错误位置的提示，与另外四组其他条件完全相同、但提供了受影响表的线索以及对注入错误的更详细描述的任务。当这些提示可用时，智能体表现显著更好，表明在大型搜索空间中导航是该任务类别的主要瓶颈（见附录D.3中的相关图10）。为了研究组合复杂性，有两个任务要求智能体在一次运行中识别所有被注入的错误，而其余六个任务各自只针对单一错误类型。当智能体必须同时检测所有错误时，性能相比聚合针对单个错误类型的独立运行结果出现了显著下降。这一发现表明，多步推理与增强的任务组合性是第二大瓶颈（见附录中D3的相关图11）。



![](https://cdn.nlark.com/yuque/0/2026/png/1739170/1786609472842-89d7f1c8-f811-4db1-92f4-862bc14bec34.png)

> **图10：有无搜索线索下的EHR数据质量审计召回率表现。**对每个智能体而言，**左侧条形为四个基础任务（仅标注了高层级错误类别名称）的平均召回率，右侧条形为四个线索变体的平均召回率**，**后者额外披露了注入的子类型以及需要检查哪些表。**每个条形为**四个错误类别各三次尝试的平均值（共12次试验）**；两个变体共享完全相同的数据、标签和评分标准，因此两者之间的差距（标注于每对条形上方）单独体现了收窄搜索范围的价值。披露查找位置对每个智能体均有帮助，并将最强模型的召回率提升至接近完美，这表明搜索空间的大小是主要的瓶颈。

![](https://cdn.nlark.com/yuque/0/2026/png/1739170/1786609499827-612e3b5f-6a0c-41f2-a964-478694907a89.png)

> **图11：EHR数据质量审计中的召回率表现：三个单错误任务分别运行与合并任务对比。左侧条形汇总了三个单错误任务**（人口统计冲突、值非法和表间不一致）的召回率，如同智能体逐一运行它们一样。真阳性在三个任务上合并计算，除以合并后的标签总数，然后取有线索和无线索变体的平均值。**右侧条形为智能体在合并任务**（有线索与无线索取平均）上的平均召回率，该任务将全部三类错误注入同一个语料库中，且标签集为三者并集。当错误类别被分开处理时，每个智能体的召回率都更高（差距标注于每对条形上方），**这表明在EHR数据质量审计中，组合负载使任务更具挑战性。**
>



临床试验匹配则呈现出一种不同的检索挑战。与 EHR 数据质量审计中搜索大型关系型数据库不同，智能体必须从约 400 份自由文本试验方案中为一名患者找出符合条件的临床试验。虽然搜索空间更小，但由于患者画像与入选标准都以非结构化文本表达，导航起来更为困难。因此，关键挑战在于在进行细粒度入选推理之前，先对语料库进行有效分诊。领先的前沿智能体与其余被测系统之间出现了明显的性能差距，即便是最强的智能体也远未达到基准饱和。运行 Opus-4.8 的 Copilot CLI 取得了最高的任务成功率（67%），其后依次为 Codex GPT-5.5（52%）、Claude Code Opus-4.8（48%），以及运行 GPT-5.5 的 Copilot CLI（44%），而其余所有智能体的得分仅在 11%–26% 之间。对最佳智能体成功轨迹的检查（Copilot CLI Opus-4.8；见附录中的相关轨迹）揭示了一种有效策略：它先用一个轻量级检索脚本对语料库进行分诊，再将入选判定分发给并行的子智能体，每个子智能体依据一份结构化的患者画像对一批互不重叠的候选试验做出裁定，随后对临界试验的标准进行集中复核，而不是依赖表层关键词匹配。直接审视召回率表现进一步凸显了该基准的难度（见图 9）。最强的智能体检索到了大多数符合条件的试验（召回率 ≈0.8–0.9），但要达到通过任务所要求的完美召回率 1.0 仍然困难，因为这需要更彻底的搜索以及对入选标准与患者画像的精确理解。



![](https://cdn.nlark.com/yuque/0/2026/png/1739170/1786609636634-ae02b2e8-9d93-49d4-8929-54f61d642fdc.png)

## 挑战：医学影像，以及 Codex GPT-5.5 的涌现能力


医学影像任务（胸部 CT 异常分类、X 光胸片报告修正以及病理全切片图像肿瘤区域选取）对每一个智能体都构成了重大挑战。在全部 Codex 与 Claude Code 智能体上取平均，**影像任务的平均成功率仅为 17%，而文本任务为 49%。影像任务上最强的智能体（Codex GPT-5.5）**在三个影像任务上的**平均成功率仅约 35%**，且没有智能体在任一单一影像任务类别上超过 40%。这在预期之中，因为智能体需要处理专门的医学模态，并应对过大的输入规模（例如一个 CT 体积通常包含数百个切片，而一张病理切片可达十亿像素级别）。智能体需要找到一种巧妙的方法将任务分解为可管理的块，并设计出分而治之的良好策略。虽然大多数智能体在这些任务上苦苦挣扎，但 Codex GPT 系列整体表现优于 Claude Code 智能体，其中 GPT-5.5 尤为突出。例如，在病理全切片图像肿瘤区域选取类别中，GPT-5.5 在 40% 的任务上取得成功，远超其他所有智能体（最佳的 Claude Code 智能体 Opus-4.8 与 Opus-4.6 仅分别达到 20% 与 17%）。检视其轨迹可发现一种类似人类病理学家审视整张切片的工作流：因为它无法直接查看十亿像素图像，它**通过 OpenSlide 图像金字塔读取切片，并渲染与评分网格对齐的下采样概览图与缩略拼图，**_**从形态学上**_**区分癌组织与良性淋巴组织，而非依赖简单的染色阈值，随后在全分辨率下逐 tile 精修肿瘤边界，并对未认领的高组织密度 tile 显式执行一遍「外围遍历」，以在提交前找回任何遗漏区域（见附录F中的相关轨迹）**。图 13 展示了一张这样的成功切片，其中 GPT-5.5 仅以两个虚假 tile 的代价恢复了整个肿瘤区域。

# 结论
---

我们提出了 HealthAgentBench，一个统一的、智能体原生的基准套件，用于在跨越患者诊疗历程的多样化数据模态与临床工作流上评估医疗 AI 智能体。该基准对当前前沿智能体而言仍然极具挑战性：即便是最强的智能体 Codex GPT-5.5，在整个套件上也仅取得 42% 的平均成功率，为未来的进展留下了巨大的空间。我们对 10 个前沿智能体的评测也揭示了当前系统的重要优势与局限，凸显了在医学影像、大型搜索空间以及复杂组合推理方面持续存在的挑战。



虽然 HealthAgentBench 为衡量与追踪医疗智能体 AI 的进展提供了一个实用接口，但我们承认该基准并未穷尽医疗智能体的所有方面，我们鼓励未来的工作加入更多的任务与模态，以更好地刻画医疗智能体 AI 能力的完整谱系，并希望它能成为一个评估未来医疗智能体的有用社区资源。

## 成功率判定标准

## EHR 数据质量审计：大海捞针的代价


另外两组明细揭示了 EHR 数据质量审计（EHR Data Quality Auditing）之所以困难的原因，两者都指向搜索空间的大小，而非任何单一难处理的错误类型。



EHR 数据质量审计（EHR Data Quality Auditing）包含八个任务，覆盖四种场景：不可能的临床取值、人口学冲突、跨表冲突/重复记录，以及一个混合了上述三者的组合任务。EHR 数据质量审计（EHR Data Quality Auditing）的每种场景都提供两种指令变体，使用相同的数据、标签和评分：一种是仅点名高层级错误族的基础任务，另一种是线索变体，其指令额外披露了所注入的具体子类型，并点名了需要检查的表。图 10 对比了两者。告诉智能体在哪里查找能提升每个智能体的召回率，最强的智能体在表被披露后达到近乎完美的召回率（Claude Code Opus-4.8 升至 0.97）。相同数据在搜索范围被收窄后变得明显更易求解，这证实了在八个表和 >800k 行中定位错误是主要瓶颈。



![](https://cdn.nlark.com/yuque/0/2026/png/1739170/1786618292588-1f19a4c0-5414-468d-a44b-1b3435671b15.png)

> **图 10：** **有/无搜索线索时 EHR 数据质量审计（EHR Data Quality Auditing）的召回表现。** 对每个智能体，左柱为四个基础任务（仅点名高层级错误族）上的平均召回率，右柱为四个线索变体上的平均召回率，后者额外披露了所注入的子类型以及需要检查的表。每根柱取四个错误族上各三次尝试的平均（12 次试验）；两种变体共享相同的数据、标签与评分，因此两者之间的差距（标注在每对柱上方）隔离出了收窄搜索所带来的价值。披露查找位置有助于每个智能体，并将最强的智能体提升到近乎完美的召回率，表明搜索空间的大小是主要瓶颈。

另一种互补的视角则追问：一次只针对一种错误类型，是否优于一次性搜索所有错误类型。组合任务将全部三个错误族注入单一语料，其标签集恰好是三个单错误任务的并集，因此唯一的区别在于智能体是一次性分诊所有内容，还是分三次有重点的遍历。图 11 对比了智能体在三个单错误任务分别运行、并把捕获结果汇总为一个聚合召回率（三个任务的真正例求和，除以汇总标签数，再在「有线索」与「无线索」变体上取平均）时的召回率，与其在组合任务上的平均召回率。分解有助于每个智能体：把相同的错误拆分为有重点的遍历，比一次性全部面对能找回明显更多的错误。这种在组合负载下的退化是 EHR 数据质量审计（EHR Data Quality Auditing）中的一项关键挑战。



![](https://cdn.nlark.com/yuque/0/2026/png/1739170/1786618319358-6e90a2af-5b36-4297-a8e5-d95656a6fe34.png)

## EHR 事件建模：AUROC 与人类工程化基线对比


EHR 事件建模（EHR Event Modelling）基准要求智能体根据纵向 EHR 事件日志预测六种新发诊断。图 12 将四个最强智能体与两个 EHRSHOT 参考点进行了对比，两者都在与智能体相同的「首次预测时刻」测试队列上评估：已发表的 CLMBR 基线（一个冻结的临床语言模型表征，接入逻辑回归头）和 count+GBM 基线（在人工工程化的计数特征上训练的梯度提升分类器）。鉴于 1 小时的时间预算，我们以 count+GBM 基线作为通过门槛，因为基于神经网络的 CLMBR 基线运行起来更昂贵且耗时。我们观察到，最强的智能体在大多数目标上可以匹敌甚至超过这两个基线，唯一的例外是胰腺癌——在该目标上 count+GBM 基线是最强的参考。

## EHR 格式转换（EHR ETL 管道定制）

+ _Workflow stage（工作流阶段）：_ Data Management（数据管理）。

+ _Expert time-to-solve（专家解题耗时）：_ 1–4 小时。
+ _Number of Tasks（任务数量）：_ 1。



**Motivation（动机）**

该任务测试智能体检查一个真实的开放源代码 **ETL** **(Extract（抽取）、Transform（转换）、Load（加载）)**仓库，并产出能够改变输出队列形态的配置的能力。它的贡献不在于上游 ETL 代码库本身，而在于将一个碎片化的、实现密集的医疗保健工作流转化为一个标准化的、可验证的智能体任务。



**Task setup（任务设置）:**

+ _**Inputs（输入，挂载为可读写）**__：_ 位于 `/workspace/MIMIC_IV_MEDS` 的陌生上游克隆；位于 `/workspace/staged_demo/raw_input` 的 demo 输入；可写的 `/workspace/output/`。
+ _**Instruction（指令，逐字给到智能体）：**_
    - 使用位于 `/workspace/MIMIC_IV_MEDS` 的代码库，对其在 `/workspace/staged_demo/raw_input` 的 demo 输入运行其 ETL 管道。检查默认抽取配置 `event_configs.yaml`，将其复制为 `custom_event_configs.yaml` 并编辑副本——保持默认配置不变、仓库的默认接线（wiring）完整——然后仅针对本次运行使用新配置运行 ETL。定制后的队列不得再将 `insurance`、`language`、`marital_status` 或 `race` 作为 admission（入院）事件上的字段存储，而必须将每一项记录为各自独立的入院时刻事件（前缀 `INSURANCE//`、`LANGUAGE//`、`MARITAL_STATUS//`、`RACE//`）；并且对门诊 OMR 测量使用 `OMR//`，对 `hosp/labevents` 使用 `HOSP_LAB//`，对 `icu/chartevents` 使用 `ICU_CHARTEVENT//`。
+ _**Required actions（所需操作）**__：_ 
    - (i) 通过复制默认配置创建新配置；
    - (ii) 编辑副本以产生所需的变换（将入院人口统计学信息作为带时间戳的事件；OMR / HOSP_LAB / ICU_CHARTEVENT 代码前缀族）；
    - (iii) 使用 `uv` 运行管道；
    - (iv) 将最终队列写入 `/workspace/output/MEDS_cohort`。
+ _**Hidden（仅验证器可见）**__：_ 位于 `/tests/` 下的金标准摘要（`gold_demo_summary.json`）与参考定制配置（`reference_custom_event_configs.yaml`）。
+ _**Submission（提交）**__：_ `/workspace/output/MEDS_cohort/` 目录树。
+ _**Limits（限制）**__：_ 智能体超时 7200 秒，验证器超时 900 秒，4 CPU，8 GB 内存，20 GB 存储，允许联网。



**Data source（数据来源）:**

+ _Upstream（上游）：_ `MIMIC_IV_MEDS`（Medical Event Data Standard，医疗事件数据标准）。
+ _Cohort（队列）：_ 公开的 MIMIC-IV demo（v2.2），公开。



**Tasks in this Category（本类别中的任务）:**

+ _Count（数量）：_ 1 个任务。



**Scoring（评分）:**

+ _**Checks**__（检查，位于 _`verify_output.py`_ 中）：_ 
    - (a) 默认配置与上游逐字节一致；
    - (b) 定制配置存在且可解析；
    - (c) 队列元数据中出现了所需的代码前缀族（`INSURANCE//`、`LANGUAGE//`、`MARITAL_STATUS//`、`RACE//`、`OMR//`、`HOSP_LAB//`、`ICU_CHARTEVENT//`）；
    - (d) 每个分片的 parquet 行数与规范内容哈希（canonical content hashes）与金标准摘要匹配。
+ _**Reward**__（奖励，成功标准）：_ 完成全部检查 (a)–(d) 得 1.0（成功）；(a)–(d) 中任一失败得 0.0（失败）。
+ _**Raw Per-trial Metrics**__（每次试验的原始指标）：_ 除二元奖励外无（验证器仅输出成功/失败）。
+ _**Hash canonicalisation**__（哈希规范化）：_ 在哈希前按 `(subject_id, time, code)` 对行排序，因此该检查对无害的写入端重排是稳健的。



**Anti-cheat & leak-proofing（防作弊与防泄漏）:**

+ _**Default-config integrity（默认配置完整性）**__：_ 检查 (a) 防止智能体通过修补上游的默认接线来走捷径绕过任务。

****

**Tasks in this Category（本类别中的任务）。**

****

**Scoring（评分）。**

+ _Per-trial（每次试验）：_ CheXprompt 以 LLM 为裁判（LLM-as-a-judge）的 5 票多数表决，针对提交的 _Findings_ 与留出（held-out）金标准。

+ _Default judge（默认裁判）：_ `gpt-5.4`。
+ _Raw Per-trial Metrics（每次试验的原始指标）：_ 平均临床显著性错误数。
+ _Gold Label Review（金标准标签审查）：_ 每个病例的金标准 _Findings_ 都对照配对的胸部 X 光片与患者的既往影像史进行了人工审查，以确保其有据可依且无临床显著性错误，因此金标准是一个可靠的修正目标。

****

**Anti-cheat & leak-proofing（防作弊与防泄漏）。**

+ _Two-service split（双服务拆分）：_ `bootstrap` 持有 PhysioNet 凭证（`PN_USER`、`PN_PASS`）；`main` 智能体服务没有任何凭证。因此，智能体无法简单地从 PhysioNet 下载金标准 _Findings_。

+ _Gating（门控）：_ `main` 在 bootstrap 通过 docker-compose 的 `service_completed_successfully` 条件干净退出后放行。

****

**Baseline observations（基线观测）：**

+ 智能体在去除草稿某个错误的同时，引入了一个幻觉出来的新发现。

## 临床试验匹配


**Tags（标签）：**

+ _Modality（模态）：_ 文本（入院记录 + 试验 XML）。
+ _Workflow stage（工作流阶段）：_ 治疗规划。
+ _Output shape（输出形态）：_ 合格的 NCT-ID 集合，按置信度排序（纯文本）。
+ _Data access（数据访问）：_ 公开（TREC-CT 2021）。
+ _Expert time-to-solve（专家解题耗时）：_ >8 小时。
+ _Number of Tasks（任务数量）：_ 9。

****

**Motivation（动机）：**  
HealthAgentBench 中的一个临床试验招募 / 资格匹配基准类别。该任务类别要求智能体阅读一份自由文本的患者入院记录与一组候选临床试验 XML，然后识别出患者符合资格的所有试验。智能体必须确保满足每一个纳入标准，且不违反任何排除标准。输出是一份按置信度排序的合格试验标识符（NCT-ID）列表。该任务测试智能体理解复杂医学资格标准、从非结构化文本中抽取相关信息，并基于结构化试验数据做出准确资格判定的能力。HealthAgentBench 的贡献在于将临床匹配任务转化为端到端工作流，并提供环境与评估框架，以针对医师判定的金标准来验证智能体的资格判定。

****

**Task setup（任务设置）：**

+ _Inputs（输入，挂载于 _`/workspace/data/`_，从主机缓存绑定挂载）：_ 位于 `/workspace/data/topic.txt` 的患者入院记录，以及位于 `/workspace/data/trials/<NCT_ID>.xml` 的该主题的判定池（judged-pool）语料库（约 300–450 个 ClinicalTrials.gov 的 XML，标准 schema）。
+ _Instruction（指令，逐字给到智能体）：_
    - 给定一名患者的自由文本入院记录与一个候选临床试验文档目录。识别出患者符合资格的所有试验——即与患者相关、满足每一个纳入标准且不满足任何排除标准。患者记录位于 `/workspace/data/topic.txt`，每个候选试验位于 `/workspace/data/trials/<NCT_ID>.xml`（标准 ClinicalTrials.gov schema）。将 `/workspace/submission/eligible_trials.txt` 写为每行一个 NCT 标识符——所有合格试验，且不含任何患者被排除在外的试验——按你的置信度降序排列。你有至多 1 小时；不要到互联网上搜索基准答案。
+ _Required action（所需操作）：_ 识别出患者符合资格的所有试验，按置信度排序。
+ _Output（输出）：_ 纯文本 NCT-ID 列表（每行一个，最可信者在前），位于 `/workspace/submission/eligible_trials.txt`。
+ _Tools（工具）：_ 标准 Python 环境；XML 解析交给智能体。
+ _Limits（限制）：_ 智能体超时 3600 秒，验证器超时 300 秒，2 CPU，2 GB 内存，4 GB 存储，允许联网。

****

**Data source（数据来源）：**

+ _Corpus（语料库）：_ TREC Clinical Trials 2021 track。
+ _Access（访问）：_ 公开。
+ _Pin（固定）：_ 75 个主题；35 832 条医师判定的 qrels；约 40 万试验的 ClinicalTrials.gov 快照，日期为 2021 年 4 月 27 日。参见 `design/related_work/clinical_trial_matching.md`。

****

**Tasks in this Category（本类别中的任务）：**

+ _Count（数量）：_ 从 TREC 2021 中选取的 9 个任务。
+ _Selection criteria（选择标准）：_ 这些任务被选取以覆盖按临床专科分层的患者画像（年龄 15–70，男女均有）。

****

**Scoring（评分）：**

+ _Raw Per-trial Metrics（每次试验的原始指标）：_ 平均 `recall_top_50`（来自智能体前 50 个最可信选取的召回率）。
+ _Reward（奖励，成功标准）：_ 当且仅当智能体 50 个最可信选取上的召回率等于 1.0（每个合格试验都在前 50 内被找回）时，试验通过（奖励 1），否则为 0。我们使用召回率而非 F1 或精确率来确定成功标准，因为在真实世界的试验招募中，遗漏一个合格试验比纳入一些不合格试验是更严重的失败。为防止智能体通过纳入一长串低置信度选取来冲高召回分数，我们施加了前 50 名的截断：智能体必须将全部合格试验排在约 400 个试验池中其 50 个最可信的选取之内才能通过。前 50 名的截断反映了试验招募者通常只有带宽审查有限短名单的实际现实，而这会偏好那些将合格试验排得更靠前的智能体，而不是将它们埋没在低置信度选取的长尾中。
+ _Gold Eligible Trials（金标准合格试验）：_ 由 TREC 的医师标注者根据该试验的 XML 与该主题的入院记录判定；为确保合格试验无歧义，我们再次人工审查判定的合格试验，并移除含有模糊且不可验证的纳入标准（例如“必须能够来到我们医院”）的试验。每个任务包含 3–9 个金标准合格试验（九个任务共 43 个）。

****

**Anti-cheat & leak-proofing（防作弊与防泄漏）：**

+ TREC 语料库是公开的；我们禁用网页浏览器，并从智能体可见路径中移除任何语料库元数据，以防止走捷径。
+ 金标准合格试验绝不对智能体可见；它们只存在于验证器中。

****

**Bootstrap & environment（引导与环境）：**

+ _Compose pattern（编排模式）：_ 每个主题的 XML 下载使用 HTTP range 请求写入 `scripts/clinical_trial_matching/assets/raw_cache/`（`.gitignored`）。
+ _Concurrency control（并发控制）：_ 一个全局主机侧 `flock` 加上一个 bootstrap 哨兵（sentinel）握手，在并发容器之间序列化抓取，使得同一主机上的多个智能体不会重复下载或在缓存上竞态。

****

**Baseline observations（基线观测）：**  
在 xhigh 努力下的 10 个前沿模型，9 个任务 × 3 次尝试 = 每个模型 27 次试验。  
四个智能体从大部队中脱颖而出：Copilot CLI 的 `opus-4.8` 以 0.667 的平均成功率领先（18/27），领先于 `gpt-5.5`（0.519，14/27）、`claude-opus-4-8`（0.481，13/27）与 Copilot 的 `gpt-5.5`（0.444，12/27）；所有其他智能体得分在 0.259 或以下。同样的四个也占据了较软的 `recall_top_50` 指标榜首（全部介于 0.82 与 0.93 之间）。

****

**Known failure modes（已知失败模式）：**

+ 智能体将排除标准误读为纳入式措辞。
+ 智能体仅用标题和摘要做分诊，却遗漏了完整 XML 中的资格细节。

## 胸部 CT 判读


**Tags（标签）：**

+ _Modality（模态）：_ 三维影像（NIfTI 体数据）。
+ _Workflow stage（工作流阶段）：_ 诊断。
+ _Output shape（输出形态）：_ 逐体数据二元标签向量。
+ _Data access（数据访问）：_ HuggingFace 在 OpenRAIL 下受控（CT-RATE）。
+ _Expert time-to-solve（专家解题耗时）：_ 1–4 小时。
+ _Number of Tasks（任务数量）：_ 10。

****

**Motivation（动机）：**  
HealthAgentBench 中的三维影像基准。该类别中的每个任务都要求智能体检查一份非增强胸部 CT 体数据，并针对一组临床发现的存在或缺失进行分类。智能体必须读取体数据、解读影像数据，并为每个请求的发现产出二元标签。这些任务测试智能体处理体积化医学影像数据、识别相关解剖结构与病理，并基于视觉证据做出准确诊断分类的能力。HealthAgentBench 的贡献在于将一个真实世界的三维影像临床工作流转化为患者影像上下文数据环境中可验证的智能体任务。智能体环境为智能体探索数据并提出策略提供了自由（例如，可联网以下载库等）。

****

**Task setup（任务设置）：**

+ _Inputs（输入，挂载于 _`/workspace/data/`_）：_ 一份非增强胸部 CT（NIfTI，200–700 层，Hounsfield 单位），位于 `/workspace/data/scan.nii.gz`；以及一份逐体数据标签列表（每行一个标签，通常 4–12 个类别），位于 `/workspace/data/labels.txt`。
+ _Instruction（指令，逐字给到智能体）：_
    - 你正处在一个包含单份非增强胸部 CT 体数据与一份待评估临床发现列表的环境中。对于列表中的每个发现，判断它在扫描中是否存在。在 `/workspace/submission/predictions.txt` 写入一个纯文本文件，对每个请求的标签写一行 `<label>: yes` 或 `<label>: no`，使用来自 `labels.txt` 的准确名称（大小写不敏感）；顺序无关紧要。仅使用磁盘上的体数据来求解；不要去查该数据集已发布的标签或报告。奖励是二元的——每个标签都必须正确。你有至多 1 小时。
+ _Required action（所需操作）：_ 检查三维体数据（规范路径为 `nibabel` → PNG 切片 → 多模态视图）并对每个请求的标签分类。
+ _Output（输出）：_ 位于 `/workspace/submission/predictions.txt` 的文本文件，每行一个 `<label>: yes/no`；顺序无关（验证器按标签名匹配）。
+ _Tools（工具）：_ 带有 `nibabel`、`pillow`、`huggingface_hub` 的标准 Python 环境。
+ _Hidden（仅验证器可见）：_ 位于 `tests/gold.json` 的金标准标签（gitignored，在引导时派生）。
+ _Limits（限制）：_ 智能体超时 3600 秒，验证器超时 300 秒，2 CPU，8 GB 内存，8 GB 存储，允许联网。

**Data source（数据来源）。**

+ _Corpus（语料库）：_ CT-RATE——25 692 份非增强三维胸部 CT 体数据，与放射科报告配对；验证集拆分为 3 038 份体数据。

**Scoring（评分）。**

+ _Compose pattern（编排模式）：_ 双服务。`main` 依赖 `bootstrap` 的成功完成。

10 行表格，全部为 xhigh，10 份体数据 × 3 次尝试 = 每个模型 30 次试验。

**Known failure modes（已知失败模式）。**

+ _Under-calling（欠呼叫）。_ 智能体渲染了合适的肺与纵隔窗，但因未见明显疾病，而将细微发现（例如间隔旁肺气肿、小结节）默认判为“缺失”——于是真实发现被遗漏。

## 病理全切片推理


**Tags（标签）。**

+ _Modality（模态）：_ 病理全切片图像（gigapixel，十亿像素）。
+ _Workflow stage（工作流阶段）：_ 研究 / 诊断。
+ _Output shape（输出形态）：_ 肿瘤瓦片坐标集合（JSON）。
+ _Data access（数据访问）：_ 公开（CAMELYON16）。
+ _Expert time-to-solve（专家解题耗时）：_ 1–4 小时。
+ _Number of Tasks（任务数量）：_ 10。

****

**Motivation（动机）。**

从周围组织中勾画出肿瘤区域是众多病理工作流的基础第一步，它支撑着广泛的下游研究与应用——生物标志物量化、分级，以及肿瘤特异性形态学特征的提取。该任务因若干原因而具有挑战性。首先，全切片图像在尺度上是 gigapixel 的，平均约为 $ 100{,}000 \times 100{,}000 $ 像素，这使得穷举式检查不可行，并迫使进行多分辨率推理：候选区域在低倍率下定位，在高倍率下确认。其次，肿瘤通常稀疏，或仅以小病灶形式存在（例如微转移或孤立肿瘤细胞簇），容易被遗漏。第三，在仅凭苏木精-伊红（H&E）染色的情况下，肿瘤与正常组织之间的边界常常模糊，以至于即便专家的标注通常也需要免疫组织化学复染的辅助。这些特性使得肿瘤勾画成为一项非平凡、决策密集的任务，需要在有限的检查预算下主动导航切片、有选择地检查局部区域并整合证据。HealthAgentBench 的贡献在于将 CAMELYON16 转变为一个可复现的、Harbor 优先的智能体任务，每张切片一个任务，隐藏的金标准分割，以及汇总到瓦片级的聚合指标。我们不要求稠密的像素级分割；相反，智能体选择其认为含有肿瘤的网格瓦片，这在许多下游研究任务中已足够。注意，CAMELYON16 包含来自乳腺癌患者的淋巴结全切片图像，其参考掩码勾画的是沉积在淋巴结中的_转移性_乳腺癌，而非原发肿瘤。由于转移灶本身就是肿瘤性组织，我们将这些被标注的区域视为待选择的肿瘤区域，此处的“肿瘤区域选择”对应于定位淋巴结肿瘤（转移）沉积。

****

**Task setup（任务设置）。**

+ _Inputs（输入，挂载进环境）：_ 一份病理全切片图像，位于 `/data/slide/current/slide.*`（金字塔式 `.tif`，通过 OpenSlide/tifffile 读取），以及公共任务行 `/workspace/benchmark_tasks.json` 中的分析网格元数据。
+ _Instruction（指令，逐字给到智能体）：_
    - 你正处在一个病理任务环境中。当前的全切片图像位于 `/data/slide/current/slide.*`，一份公共任务行位于 `/workspace/benchmark_tasks.json`，一份可编辑的提交位于 `/workspace/submission.json`。分析网格使用降采样 16 下的 `256x256` 瓦片，因此每个网格瓦片跨越 `4096x4096` 全分辨率（level-0）像素。识别出全部且仅有含有肿瘤的瓦片，并用形如 `{"x": <int>, "y": <int>}` 的整数网格坐标对象填充 `predicted_tumor_tiles`；将非组织瓦片视为非肿瘤。你有 1.5 小时预算；不要到网上查找解决方案，也不要训练或微调模型。
+ _Required action（所需操作）：_ 在固定的 $ 256\times 256 $ 网格、降采样 16 下预测完整的肿瘤瓦片集合；若一个瓦片 ≥ 20% 的面积为肿瘤，则该瓦片为“肿瘤”。
+ _Output（输出）：_ 位于 `/workspace/submission.json` 的 JSON，含 `predicted_tumor_tiles`，一个 `{x, y}` 网格坐标对象列表。（一个 `contains_tumor` 布尔值也被记录，但此处不计分。）
+ _Tools（工具）：_ 默认情况下——我们基线所使用的配置——智能体通过 OpenSlide/tifffile 读取切片本身，没有辅助脚本。
+ _Hidden（仅验证器可见）：_ 位于 `/tests/` 下的金标准肿瘤掩码（绝不挂载进 `main`）。
+ _Limits（限制）：_ 智能体超时 5400 秒，验证器超时 3600 秒，2 CPU，8 GB 内存，20 GB 存储，允许联网。

****

**Data source（数据来源）。**

+ _Corpus（语料库）：_ CAMELYON16（AWS S3 公开镜像，位于 `s3://camelyon-dataset/CAMELYON16/`）；切片为金字塔式 `.tif`，通过 OpenSlide 读取。
+ _Access（访问）：_ 公开，无需凭证。

****

**Tasks in this Category（本类别中的任务）。**

+ _Count（数量）：_ 10 个任务，每个包含一个 CAMELYON16 肿瘤切片。
+ _Selection（选择）：_ 这些切片继承自 CAMELYON16 的一系列肿瘤大小（金标准区域跨约 20–160 个瓦片）以及多样的转移形态；即便是强智能体也会遗漏较小的沉积。

**Scoring（评分）。**

+ _Reward（奖励，成功标准）：_ 计算预测瓦片集合相对隐藏金标准掩码的瓦片级 F1；当且仅当 tile-F1 ≥ 0.90 时试验通过（奖励 1.0），否则为 0.0。我们选择 0.9 的 F1 而非 1.0 的 F1，是为了容许因肿瘤边界的模糊性所造成的一些微小差异。
+ _Raw Per-trial Metrics（每次试验的原始指标）：_ 瓦片级 F1。

****

**Anti-cheat & leak-proofing（防作弊与防泄漏）。**

+ _Gold isolation（金标准隔离）：_ 金标准肿瘤掩码位于 `/tests/` 下（仅验证器可见）。
+ _Credential surface（凭证面）：_ 无（数据集为公开）。

****

**Bootstrap & environment（引导与环境）。**

+ _Compose pattern（编排模式）：_ 双服务（一次性 `bootstrap` 然后 `main`），将公开数据以懒加载方式下载到 `scripts/tumor_area_selection_pathology/assets/raw_cache/`（gitignored 的共享主机缓存）。
+ _Cache sharing（缓存共享）：_ 同一主机上的多个容器共享缓存，因此 gigapixel 切片每个主机只下载一次，而不是每次试验都下载。

****

**Baseline observations（基线观测）。**  
在 xhigh 努力下的 10 个前沿模型，10 个任务 × 3 次尝试 = 每个模型 30 次试验。  
`gpt-5.5` 领先，以最高的 tile-F1（0.845）通过 12/30（平均成功率 0.400），且是唯一一个超过 0.30 的智能体。  
`claude-opus-4-8` 以 0.200（6/30）紧随其后；三个模型以 0.167（5/30）并列：`claude-opus-4-6`、`gpt-5.3-codex` 与 Copilot 的 `opus-4.8`，其余依次落后（Copilot 的 `gpt-5.5` 4/30；`claude-opus-4-7` 与 `claude-sonnet-4-6` 3/30；`gpt-5.4` 2/30；`gpt-5.4-mini` 0/30）。  
通过门槛（tile-F1 ≥ 0.90）要求很高：`gpt-5.4-mini` 取得了 0.967 的瓦片召回率，但精确率仅 0.320（它过度选择了瓦片），因此其 tile-F1（0.481）从未跨过门槛。

**Known failure modes（已知失败模式）。**

+ 智能体通过缩略图草草浏览，遗漏了小的肿瘤病灶。
+ 智能体将组织伪影过度分割为肿瘤。
+ 智能体将邻近的良性组织（例如炎症）与肿瘤混淆。

## EHR 事件建模（纵向临床事件预测）
****

**Tags（标签）。**

+ _Modality（模态）：_ 纵向 EHR 时间线（表格化事件）。
+ _Workflow stage（工作流阶段）：_ 研究。
+ _Output shape（输出形态）：_ 逐患者概率（CSV）。
+ _Data access（数据访问）：_ Redivis 受控（Stanford STARR via EHRSHOT）。
+ _Expert time-to-solve（专家解题耗时）：_ 4–8 小时。
+ _Number of Tasks（任务数量）：_ 6。

****

**Motivation（动机）。**  
该任务类别在 HealthAgentBench 中以纵向临床事件预测挑战智能体。智能体必须从带标签的训练数据中学习一个预测规则，并将其应用到无标签的留出测试集。HealthAgentBench 的贡献在于将 EHRSHOT 原始时间线基准打包为一个可复现的、Harbor 优先的任务族，具有一键式的容器侧数据下载、由 docker-compose 卷拓扑强制执行的隐藏测试标签、在事件切片上的机械化防泄漏，以及通过基线即成功/失败的门控。

****

**Task setup（任务设置）。**

+ _Inputs（输入，挂载于 _`/data/`_）：_ 训练标签（`train_labels.csv`）、验证标签（`val_labels.csv`）、一个无标签测试集（`test_examples.csv`，无标签），以及纵向事件日志的一个逐任务防泄漏切片（`events.csv`；对于测试患者，仅保留满足 $ {\rm start} < T_{\rm first} $ 的事件）。注意，该测试集不同于原始的 EHRSHOT 测试集：我们取原始测试集，仅保留每个测试患者的第一个预测时刻事件切片，因此智能体必须从部分时间线出发、在没有任何未来信息的情况下进行预测。
+ _Instruction（指令，逐字；所示为高脂血症目标）：_
    - 预测患者是否会在接下来的一年内首次被诊断高脂血症（代码 `SNOMED/55822004` 及其本体子节点）。预测在出院当天晚上 11:59 做出；患者已有该诊断的出院记录被忽略。从带标签的 `train` 与 `val` 拆分中学习一个策略，并将其应用到未提供标签的留出 `test` 拆分，仅使用 `start` 早于每个预测时刻的事件。将 `/workspace/submission/predictions.csv` 写为含有列 `patient_id,prediction_time,probability`（在 $ [0,1] $ 内连续）的文件。按 AUROC 计分。你有 1 小时，且可联网。
+ _Required action（所需操作）：_ 从 train + val 学习一个预测策略，应用到测试集。
+ _Output（输出）：_ 位于 `/workspace/submission/predictions.csv` 的逐患者概率，列为 `patient_id,prediction_time,probability`；按 AUROC 计分。
+ _Hidden（仅验证器可见）：_ 测试标签位于一个 `/tests/` 挂载，该挂载_不_挂载进 `main`；Redivis API 令牌绝不抵达 `main`。
+ _Limits（限制）：_ 智能体超时 3600 秒（1 小时预算），验证器超时 300 秒，16 CPU，64 GB 内存，65 GB 存储。`main` 内部_启用_互联网。

****

**Data source（数据来源）。**

+ _Corpus（语料库）：_ EHRSHOT，基于 Stanford STARR EHR 队列（6 739 名患者，41.6M 次观测）。
+ _Access（访问）：_ Redivis 受控；通过 `~/.redivis/api_token` 访问。
+ _Pin（固定）：_ 每个任务切片约 4 GB 的 Redivis 包。参见 `design/related_work/ehrshot_2307.02028.md`。

****

**Tasks in this Category（本类别中的任务）。**

+ _Count（数量）：_ 6 个任务。
+ _Selection Criteria（选择标准）：_ 我们从 EHRSHOT 基准中选取 6 个聚焦于新发诊断预测的任务（高脂血症、乳糜泻、急性心肌梗死、胰腺癌、系统性红斑狼疮（SLE）、原发性高血压）。

****

**Scoring（评分）。**

+ _Reward（奖励，成功标准）：_ AUROC 在智能体的提交与留出测试标签上计算。当且仅当 AUROC ≥ 该任务的 count+LightGBM 基线（在生成器中硬编码的逐任务基线 JSON）时得 1，否则为 0。
+ _Raw Per-trial Metrics（每次试验的原始指标）：_ 测试 AUROC。

****

**Anti-cheat & leak-proofing（防作弊与防泄漏）。**

+ _Event-slice integrity（事件切片完整性）：_ 对于测试患者，仅保留满足 `start < T_first`（患者的第一个预测时刻）的事件，且任何未来的 `end` 值被置空；train/val 患者保留其完整时间线。
+ _Test-label isolation（测试标签隔离）：_ 测试标签绝不提交到 git；bootstrap 将它们写入 `main` 看不到的 `/tests/` 挂载。

****

**Bootstrap & environment（引导与环境）。**

+ _Compose pattern（编排模式）：_ 双服务。`bootstrap` 读取 `~/.redivis/api_token`，下载约 4 GB 的包，切分事件日志，划分拆分，将测试标签写入 `/tests/`，然后终止。
+ _Resource profile（资源画像）：_ 16 CPU、64 GB 内存、65 GB 存储——套件中最昂贵的任务。

****

**Baseline observations（基线观测）。**

在 xhigh 努力下的 10 个前沿智能体，6 个目标 × 3 次尝试 = 每个智能体 18 次试验。`claude-opus-4-7` 以 0.778 的平均通过率领先（14/18），Codex `gpt-5.5` 与 Copilot 的 `opus-4.8` 紧随其后（均为 0.722，13/18），`claude-opus-4-8` 与 Copilot 的 `gpt-5.5` 略后（均为 0.667，12/18）；另有三个以 0.611 并列（11/18）：`claude-sonnet-4-6`、`gpt-5.3-codex` 与 `gpt-5.4`。`gpt-5.4-mini` 以 0.389（7/18）落后，最弱的 `claude-opus-4-6` 仅通过 0.333（6/18），在套件中最长的墙上时钟（wall-clock）下发生了 7 次智能体超时。所有智能体的平均测试 AUROC 都紧挨在一起（0.72–0.77），因此造成差异的是通过基线门控，而非原始判别力。每次试验的成本范围从 $ 0.80（`gpt-5.3-codex`）到  $3.32（`gpt-5.5`）。

****

**Known failure modes（已知失败模式）。**

+ _Overfitting on rare outcomes（对稀有结果的过拟合）。_ 在阳性样本很少时（例如乳糜泻仅有约 11 个验证阳性），智能体调出一个在其自身验证上表现良好、却在留出测试集上崩溃的特征/集成混合模型——GPT-5.5 最好的乳糜泻模型从约 0.74 的验证 AUROC 跌到测试的 0.30，_低于随机_。
+ _Self-inflicted validation leakage（自作自受的验证泄漏）。_ 智能体自身的评估 harness 发生泄漏（例如集成分数跨折（fold）渗透），夸大了其 AUROC 估计，并掩盖了泛化差距，直到留出测试将其暴露。
+ _Resource exhaustion（资源耗尽）。_ 较弱的智能体在流式读取多 GB 事件日志（`events.csv` 约 2.1 GB）时超时，未产生任何提交。

## EHR 数据质量审计


**Tags（标签）。**

+ _Modality（模态）：_ 表格化 EHR。
+ _Workflow stage（工作流阶段）：_ 数据管理。
+ _Output shape（输出形态）：_ 被标记行的 CSV（`table,_row_id`）。
+ _Data access（数据访问）：_ 公开（MIMIC-IV demo + 合成错误）。
+ _Expert time-to-solve（专家解题耗时）：_ >8 小时。
+ _Number of Tasks（任务数量）：_ 8。

****

**Motivation（动机）。**

该任务类别在 HealthAgentBench 中引入了一个数据质量审计基准。智能体充当结构化 EHR 数据集的审计员，标记违反临床合理性的行。HealthAgentBench 的贡献在于一个确定性的、可复现的合成错误基准，带有隐藏标签、源名混淆，以及将簇级召回率与行级精确率相结合的计分方式。



**Task setup（任务设置）。**

+ _Inputs（输入，挂载于 _`/workspace/data/csv/`_）：_ 损坏的 EHR-demo 子集，以 gzip 压缩的 CSV（`<table>.csv.gz`）形式，跨越 8 张医院与 ICU 表。这些损坏由一个确定性的合成错误配方生成，在 Docker 构建时设定随机种子，包含以下错误类型：不可能值（量程极值、小数移位、单位混淆与单位标签不匹配）、不一致（表内与跨表的冲突/重复记录），以及人口统计学矛盾（与其他记录相矛盾的患者人口统计学信息）。
+ _Instruction（指令，逐字；所示为人口统计学冲突任务）：_
    - 你正处在一个任务环境中，其中包含 `/workspace/data/` 下的一个 EHR 数据集副本。做一次数据质量检查，并标记属于某些错误类别的数据录入错误。标记该类别中的所有错误_人口统计学矛盾_——患者被记录的人口统计学信息与其他关于该患者的证据相矛盾。提交一份位于 `/workspace/submission/flagged_rows.csv` 的 CSV，列为 `table` 与 `_row_id`。你有至多 1 小时；不要到互联网上查找解决方案。
+ _Instruction disclosure（指令披露）：_ 基础指令指明了错误族，而非其子类型；`_clues` 变体则额外披露子类型与待检查表。
+ _Required action（所需操作）：_ 标记智能体认为有问题的行。
+ _Output（输出）：_ 模式为 `table,_row_id` 的 CSV，位于 `/workspace/submission/flagged_rows.csv`。
+ _Limits（限制）：_ 智能体超时 3600 秒，验证器超时 600 秒，2 CPU，4 GB 内存，10 GB 存储，允许联网。

****

**Data source（数据来源）。**

+ _Corpus（语料库）：_ MIMIC-IV demo（v2.2），在 Docker 构建时施加一个确定性的合成错误注入配方。
+ _Pin（固定）：_ 合成错误配方设定了种子；金标准随损坏一同派生。

****

**Tasks in this Category（本类别中的任务）。**

+ _Count（数量）：_ 8 个任务。
+ _Task Names（任务名称）：_ 四个基础子任务，加上每个的指令披露（`_clues`）变体。四个基础子任务是：`task_impossible_value`、`task_inconsistency`、`task_demographic_conflict` 与 `task_combined`。`task_combined` 任务混合了全部三个错误族。每个子任务的 `_clues` 变体在数据、标签与计分上完全相同，但指令额外指明了注入的子类型与待检查表。

****

**Scoring（评分）。**

+ _Reward（奖励，成功标准）：_ 当且仅当簇级召回率为 1.0（每个被注入的错误簇至少有一个被标记成员）时，试验通过。我们选择召回率是因为真实数据库中可能已存在错误。为防止智能体用假阳性淹没提交，我们还要求精确率至少为 0.01。
+ _Raw Per-trial Metrics（每次试验的原始指标）：_ 平均簇级召回率。一个簇是构成单个被注入错误的所有行的集合（例如一组冲突记录）。平均簇级召回率计算为：至少有一个行被智能体标记的簇所占的比例。
+ _Gold（金标准）：_ 对照由错误注入配方产生的隐藏金标准集合。我们人工审查每个错误，以确保它是应当被标记的真实错误。

****

**Anti-cheat & leak-proofing（防作弊与防泄漏）。**

+ _Source-name obfuscation（源名混淆）：_ 智能体可见的 CSV 文件名被重命名；“MIMIC”一词不出现在任何智能体可见的路径中。
+ _Instruction-level prohibition（指令级禁止）：_ 智能体被要求不去获取上游数据集；结合源名混淆，这就是对抗拉取干净副本的实时防御。（一个计划中的 `/etc/hosts` 出口（egress）封锁当前未激活，因为 `/etc/hosts` 在镜像构建时是只读的。）

****

**Bootstrap & environment（引导与环境）。**

+ _Compose pattern（编排模式）：_ 单服务 Docker。
+ _Build-time work（构建期工作）：_ demo CSV 在构建时使用设定种子的合成错误配方被确定地下载并损坏；金标准集合随之计算，并由验证器持有。

**Baseline observations（基线观测）。**

汇总的平均召回率给了我们另一个角度：大多数智能体找回了被注入错误簇的绝大部分（最强的超过 0.85 的平均召回率），却很少能抓住任务中的_每一个_簇。由于通过门控要求簇召回率 = 1.0，这些高召回但不完整的运行仍然得 0 分。

# 附录 F 成功试验的轨迹分析
---

为了定性地理解最强智能体是如何求解 HealthAgentBench 任务的，我们为每一基准类别采样了表现最佳智能体的轨迹（trajectory），其中记录了每一条推理消息、shell 命令与观测。本附录逐类别地走查一条具代表性的成功轨迹，并总结每个智能体采用的策略。



一个反复出现的行为特征贯穿全部七个任务类别：最强的智能体把大部分步骤花在定向与核验上——枚举工作区、阅读源代码/数据、检查自己的中间输出，而不是盲目地生成代码或答案。下面的按类别小节将使这一点变得具体。

## EHR 格式转换：最小作用域的配置覆写


**最佳智能体：** Codex GPT-5.5（成功率 100%；59 步，$1.01）。该任务要求智能体让一个 MIMIC-IV→MEDS 的 ETL 输出一个队列，其中入院人口学特征变为独立的人院时刻事件，且各测量域带有不同的代码前缀。智能体一开始就陈述其计划——「先检查仓库接线与配置，再做最小作用域的改动」——并在做任何编辑之前，把运行的前三分之一时间花在阅读上：

```latex
pwd && rg --files                                   # 枚举仓库
sed -n '1,240p' .../configs/event_configs.yaml      # 读取默认配置
find /workspace/staged_demo/raw_input -type f       # 检查暂存输入
cp .../event_configs.yaml .../custom_event_configs.yaml   # 复制，而非编辑
```



随后它只修补被复制的配置和一个 CLI 覆盖项（「默认 YAML 保持不动，仍是回退方案」），运行 ETL，并验证生成的 parquet 内容——而不仅仅是退出码——最后再做一次 `git status` 扫描以留下最小差异。这个「定向 → 作用域 → 执行 → 验证 → 清理」循环是其他任务所依循的模板。

## 临床试验匹配：先分诊，再并行资格判定


**最佳智能体：** Copilot CLI Opus 4.8（成功率 67%）；所采样的 `task_19` 试验召回率为 1.0。面对一名患者的 301 份候选试验 XML——一名 65 岁男性，患有冠心病（CAD）和既往心肌梗死（MI）、复发性持续性单形性室速（VT）、晕厥、有症状的心动过缓，以及一次复苏成功的心脏骤停，因导管插入术和电生理检查入院——Opus-4.8 编排器并不亲自阅读每一份试验，而是用代码进行分诊，然后把资格判定分发给并行子智能体：

1. **脚本化分诊。** 它编写了一连串内联 Python 遍历全部 301 份 XML——解析每份试验的标题、条件、年龄/性别限制与标准；应用硬性人口学过滤（年龄 65、男性）；根据心脏病学关键词组（VT/心律失常、ICD/SCD、晕厥、CAD/MI、cath/PCI、HF、HTN、HLD）评分相关性；并把存活下来的相关子集拆分为五个互斥批次。
2. **并行判定。** 它派生出五个后台 `general-purpose` 子智能体，每批一个，每个都被提示为「临床试验资格判定器」，并配有一个结构化的患者档案。关键在于，该档案明确说明了患者没有的病症——「无房颤……目前没有 ICD 或起搏器（只有一个循环记录仪）……非缺血性心肌病」——从而每个子智能体都能在其批次内一致地应用排除标准。
3. **合并与再核实。** 它收集每个子智能体的判定结果，然后亲自重新阅读存活下来和处于边界的试验的完整资格文本（例如完整提取 DAVID II 的标准）以解决边缘情况，随后以置信度降序写入 `eligible_trials.txt`，附带一份有记录的患者摘要，并验证每个 NCT ID 都能对应到真实的试验文件。



这种并行子智能体编排与单线程的 Codex 智能体（次佳，任务成功率 52%）形成对照，后者阅读的试验少得多，但在一个上下文中读到了正确的那些。Opus-4.8 则用代码进行广泛分诊，并行化逐试验判定，然后在中心位置重新检查边界判定。由于通过门槛奖励召回率（找回每一个符合条件的试验），这种「先广撒网再核实」的扇出策略收到了成效：它找回了全部四个金标准合格试验（召回率 1.0，即通过），代价是精确率（0.40；在十个选择中有六个假阳性）。

## EHR 事件建模：防泄漏的 ML 流水线


**最佳智能体：** Claude Code Opus-4.7（成功率 78%；所采样的试验以高于基线的 AUROC 通过）。该智能体必须在一个多 GB 的事件日志上构建机器学习流水线，并击败基线 AUROC。其总结把握了要点：「用 pyarrow 加载了 29M 事件（约 8s），并构建了按患者排序的时间线；为每个（患者，预测时刻）对提取了特征」，且只使用截断时间之前的事件。Codex GPT-5.5 以相当的质量用同样的方式求解，并叙述了关键的工程决策：它探查已安装的技术栈（「XGBoost 已安装，LightGBM……因缺少 `libgomp` 而无法使用」），使用 Polars 惰性连接（lazy joins）按患者和截断前时间将 2930 万行的日志关联到预测行表（「4220 万条截断前事件行对……约 2.4 秒」），并在特征表内部强制执行防泄漏截断，以构建干净的训练数据用于泛化。两个智能体都把数据泄漏当作构建训练数据的结构性不变量来对待，而非事后补救，从而获胜。

## 胸部 CT：多窗口渲染与噪声控制


**最佳智能体：** Codex GPT-5.5（成功率 33%；所采样的试验以 1.0 准确率通过）。由于智能体无法直接看到三维体积，其全部策略就是制造正确的视图：它读取体素间距，然后渲染裁剪后的肺窗与纵隔窗联系表（contact sheet）、轴位/冠状位/矢状位重组，并——为了对抗非增强噪声——「穿过纵隔的小 z 层块均值图像」，再辅以对可疑液囊的 HU 测量。它按标签逐一推理（积液、食管裂孔疝、淋巴结病、肺不透光/实变），在证据模糊时有意做出保守的二元判定，最后做一次格式检查，确保每个被请求的标签恰好出现一次且带有 `yes`/`no` 值。瓶颈在于感知落地（perceptual grounding），而智能体的优势来自有纪律的视图生成，而非额外的搜索。

## 病理全切片：多分辨率分块与形态学驱动的判定


**最佳智能体：** Codex GPT-5.5（成功率 40%；所采样的 `slide_0001` 试验以 0.967 的 tile-F1 通过，163 个真正例分块且无一遗漏）。该智能体必须标记一幅十亿像素病理全切片图像（whole-slide image）中的哪些分块含有肿瘤，评分依据为分块 F1 与肿瘤覆盖度。与胸部 CT 异常分类（CT Abnormality Classification）类似，它无法直接查看切片，因此其整体策略是制造多放大倍率下对齐的视图，然后进行形态学推理：

1. 它通过 OpenSlide 金字塔读取切片，并渲染与评分网格对齐的多个层级视图——一幅带有分块网格标注的低倍（level-6）概览，外加每个区域的 level-4 与 level-2 联系表——并声明它将「生成与 4096 像素网格对齐的下采样视图，以便针对所需坐标做出肿瘤分块判定」。
2. 它通过组织学而非颜色阈值来区分肿瘤与干扰因素：「肿瘤与淋巴组织必须按形态学判定」，识别出「左侧大肿块为癌，而上方的网状/暗区主要为淋巴或非肿瘤」，并仅为了计算每个分块的组织/染色占比以避免对低组织边缘区域过度判定。
3. 随后它逐分块细化边界——以完整 level-2 分辨率检查模糊的「过渡行……下缘处的癌」混入淋巴组织的位置——并对其尚未认领的高组织分块执行一次「外部遍历」以捕获任何被遗漏的癌，在将最终选区叠加到概览之上后，把分块坐标写入 `submission.json`。

该轨迹几乎与胸部 CT 异常分类（CT Abnormality Classification）完全相同：瓶颈在于感知落地（perceptual grounding），智能体的优势来自有纪律的多分辨率视图生成与边缘细化，而非任何已训练的（learned）分类器——没有训练任何模型；每次判定都是对一幅渲染分块的视觉判断。下图展示了该策略在单张切片上的结果，其中 Codex GPT-5.5 仅用两个虚假分块就找回了整个肿瘤区域（tile-F1 0.967）。

## X 光胸片：阅读既往史，让图像说了算


**最佳智能体：** Codex GPT-5.4（任务成功率 40%）。我们采样了一条仅 24 步、$0.314 的成功轨迹。这是整套任务中最省成本的通关轨迹。智能体识别目标检查，阅读草稿 `FINDINGS` 与既往报告以列举有争议的主张，然后参考胸部 X 光片来解决具体的矛盾，而非整体重写：「图像证实了严重的过度充气/肺气肿性改变，无急性局灶性气腔疾病、胸腔积液或气胸。」它只编辑被矛盾的句子，然后做一次 JSON 回读。将每次修正都扎根于图像（且不动其他内容）的纪律，正是「仅编辑」评分所奖励的。

## EHR 数据质量审计：脚本化检测与迭代式召回恢复


**最佳智能体：** Claude Code Opus-4.6（成功率 42%；所采样的 `task_demographic_conflict` 试验以对错误的完全召回通过）。该智能体检查八个 gzip 压缩的表，然后编写并迭代细化一个用于人口学冲突的 Python 检测器：

```latex
for f in /workspace/data/csv/*.csv.gz; do zcat "$f" | head -3; done   # schema
python analyze.py        # 第一遍检测器
python analyze2.py       # 更深入：性别特异性实验室检查、参考范围、身高
python analyze3.py       # 最终全面扫描
```



它的优势在于通过迭代实现召回恢复：在初次遍历后，它特意「更深入地挖掘性别特异性实验室检查……以及其他人口学矛盾」，捕获两名患者被遗漏的血红蛋白（Hemoglobin）行，在后续遍历中发现另一名性别不匹配的患者，然后才重建提交——并验证每个被标记的行的 id 都存在于源数据中。这在单一错误族上收到了成效，但正如相关章节和附录所示，没有任何智能体能在组合任务上持续做到这一点。

## 共同主题


两项定性模式贯穿全部七个任务。第一，验证是第一等公民活动：成功的智能体阅读源代码与产物，重新检查边界判定，并扫描其差异，把远多于写代码的步骤花在检查上。第二，策略是根据任务的真实瓶颈来塑形的——针对 ETL 的最小配置覆盖、针对试验检索的「脚本化分诊 + 标准级推理」、针对预测构建训练与验证集的防泄漏连接、针对影像任务（CT 窗宽窗位与全切片分块）的多分辨率视图生成、针对报告修正的以图像为根基的编辑，以及针对数据质量审计的迭代式召回恢复。
